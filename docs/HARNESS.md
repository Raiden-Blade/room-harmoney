# Room Harmony 開発ハーネス（15.1 準拠）

本書は、要件定義書「Room Harmony — アプリ開発プロンプト」**15.1 開発ハーネス**の実体である。
生成（実装）と検証（QA）を分離した「テストゲート方式」で開発を進めるための、役割・ゲート・証跡・前進/停止条件を定義する。

> 本書は**プロセス定義**であり、受け入れ条件（DoD）そのものは定義しない。合否判定は必ず要件定義書「**18. テスト方針・受け入れ条件（DoD）**」に紐づける。DoD の再定義・変更は**人間の承認を必須**とする。

## 1. 2つのサブエージェント（独立させる）

| 役割 | 定義ファイル | 責務 | できること | してはいけないこと |
|---|---|---|---|---|
| **実装エージェント** | `.claude/agents/rh-implementer.md` | 要件に沿って機能を実装 | コード編集、実装、単体テストの作成 | ゲート合否の自己判定、テストの緩和/削除 |
| **QA / レビューエージェント** | `.claude/agents/rh-qa-reviewer.md` | 実装から独立して成果物を検証 | テスト実行、ブラウザ自動操作でのE2E、証跡収集、合否判定 | 実装コードの修正（＝独立性の担保） |

**独立性のルール**
- QA エージェントは**実装コードを変更しない**。不具合は「指摘（reports）」として返し、修正は実装エージェントが行う。
- QA エージェントは、実装エージェントの主張ではなく**自ら実行した結果**（テスト出力・スクショ・ログ）だけを根拠に合否を出す。

## 2. 段階別ゲート（15.1 + 18章）

アプリが起動可能になる前は単体/結合をゲートにし、フロントが動く段階で E2E を加える。

| 段階 | 対象 | ゲート種別 | 主なDoD紐づけ（18章） |
|---|---|---|---|
| G1 ロジック | 推薦（リフト算出・ハイブリッド並び順）、経路（最短経路・巡回順） | **単体テスト** | 18.1 単体 |
| G2 API | 主要エンドポイント（17章）のreq/res・バリデーション | **結合テスト** | 18.1 結合 / 17章 |
| G3 フロント結合 | 画面がAPIと結合して表示される | 結合 + 手動スモーク | 18.2 各項 |
| G4 E2E ハッピーパス | QR起点→商品詳細→関連/コーディネート→ルート→ログ記録 が一気通貫 | **E2E（実ブラウザ）** | 18.1 E2E / 18.2 全項 / 18.3 DoD |

**カメラQR読取の E2E（15.1 特記）**
自動テストで実カメラは使えないため、次のいずれかで検証する。
1. **URL直リンク・フォールバック**（要件4.1）経由で同一画面に到達 ← 既定
2. 擬似カメラ入力（`getUserMedia` のモック／既知QR画像の注入）

## 3. 受け入れ条件チェックリスト（18章 → ゲート対応）

各項目は QA エージェントが検証し、`harness/reports/` に合否・証跡パスを記録する。

| ID | 受け入れ条件（18.2 / 18.3） | ゲート | 証跡 |
|---|---|---|---|
| AC-1 | 商品QRを読むと商品詳細＋**リフト順**の関連商品が表示。カメラ不可時はURL直リンクで同一画面に到達 | G4 (+G1並び順はG1) | スクショ + テスト出力 |
| AC-2 | スキャン商品を含むコーディネートが1件以上表示され、構成商品と合計金額目安が見える | G4 | スクショ |
| AC-3 | QR起点→目的商品の経路が地図上に線で描かれ、経由サブ通路が示される | G4 (+G1経路はG1) | スクショ + テスト出力 |
| AC-4 | 上記操作すべてがイベントログに記録され、`experiment_group`（A/B割付）が付与される | G2/G4 | ログ抽出 + テスト出力 |

## 4. 証跡（エビデンス）の残し方

- 保存先：`harness/evidence/<段階>/<AC-ID>/`（スクショ・ログ・テスト出力）
- レポート：`harness/reports/gate-<G番号>-<日付>.md`（各ACの合否・証跡相対パス・再現コマンド）
- スクリーンショットは QA エージェントがブラウザ自動操作で取得し、対応する AC-ID とタイムスタンプをファイル名に含める。

## 5. 前進条件 / 停止条件（15.1）

**前進条件（Advance）**
- 当該段階のゲートに含まれる受け入れ条件を**すべて満たし**、テストが**緑**のときのみ次段階へ進む。
- テストの**緩和・削除で通すことは禁止**。見かけの合格は不合格として扱う。
- 受け入れ条件（DoD）自体の変更は**人間の承認**を必須とする。

**停止条件（Stop / Escalate）**
- 同一段階で **3回**修正しても不合格なら、無限ループを避けて**人間にエスカレーション**する。
- エスカレーション時は `harness/reports/` に「症状・試した修正・残る失敗・推定原因」を記録する。

**修正ループ（1段階内）**
```
実装エージェント: 実装/修正
        │
        ▼
QA エージェント: ゲート実行（単体/結合/E2E）＋証跡収集
        │
   ┌────┴────┐
 緑 │        │ 赤
   ▼         ▼
次段階へ   指摘をreportsに記録 → 実装へ差し戻し（試行回数+1）
                     │
              3回超過 → 人間へエスカレーション
```

## 7. 起動の号令（オーケストレーション手順）

親（オーケストレータ）は各段階で以下を回す。

1. **宣言**：その段階で「作るもの・前提・想定成果物」を短く宣言（15章）。
2. **実装**：`rh-implementer` を起動して実装。
3. **検証**：`rh-qa-reviewer` を起動し、該当ゲートを実行させて合否と証跡を受け取る。
4. **判定**：緑→前進宣言。赤→差し戻し（§5のループ）。
5. **記録**：`harness/reports/` にゲートレポートを残す。
