## G-P2C-4: inbound受け口（独立確認）

`backend`（`uvicorn app.main:app --port 8000`）と`frontend`（`npm run dev` port 5173、
`VITE_CHATBOT_BASE_URL`未設定＝既定の`https://example.invalid/chatbot`を使用）を実起動し、
Claude_Browser MCPで直接URL遷移させ、`get_page_text`/`read_page`のテキスト証跡を取得した

検証した優先順位（4.4章記載どおり: `product_id` → `coordinate_id` → `to_product` → QR直リンク）:

1. `?product_id=P001&coordinate_id=C001&to_product=P011` → **S2（商品詳細, P001）** へ遷移
   （product_idが最優先であることを確認）。
2. `?coordinate_id=C001&to_product=P011` → **S3（コーディネート詳細, C001）** へ遷移
   （coordinate_idがto_productより優先されることを確認）。
3. `?qr_id=QR-PRODUCT-P001&to_product=P011` → **S4（ルート画面, P011宛）** へ遷移
   （to_productがQR直リンクより優先されることを確認。P011はfloor=2の商品）。
4. セッションあり + `?to_product=P011`単独 → S4へ遷移し、実際に`GET /api/route`が
   呼ばれ跨フロア経路が描画される（フロア切替UI・乗換表示が表示、詳細はG-P2C-6参照）。
5. セッションなし + `?to_product=P011` → S4へ遷移自体は行われ、遷移先が来店ロックUI
   （`visit-lock`）を表示する（AC-5との整合、4.4章の「遷移先の画面が来店ロックUIを表示する」仕様どおり）。

既存 `?product_id=`/`?coordinate_id=` の回帰確認:
- `GET /s/QR-PRODUCT-P001`（QR解決経由、ディープリンクとは別経路）でS2に正しく到達し、
  リフト順の関連商品・コーディネートが表示されることを確認（既存機能の回帰なし）。
- `frontend`のvitestでも`ScanPage.test.tsx`の既存4件（URL直リンク fallback）が

## G-P2C-5: chatbot往復（4.4）

outboundリンク（`ChatbotLink`）のhrefを実ブラウザで4画面について確認した:

| 画面 | 確認したhref |
|---|---|
| S1店内トップ（scan_entrance） | `https://example.invalid/chatbot?screen=scan_entrance` |
| S2商品詳細（product_detail） | `https://example.invalid/chatbot?product_id=P001&screen=product_detail` |
| S3コーディネート詳細（coordinate_detail） | `https://example.invalid/chatbot?coordinate_id=C001&screen=coordinate_detail` |
| S4ルート画面（route） | `https://example.invalid/chatbot?to_product=P011&screen=route` |

いずれも、その画面に到達した際のinboundコンテキスト（product_id/coordinate_id/to_product）と
同じキー・値がoutboundリンクに引き継がれている（往復導線の成立を確認）。個人情報・購入情報は
含まれていない（product_id/coordinate_id/to_product/screenの4項目のみ）。

`chatbot_open`イベントpayloadの内容は、QAが独立に実行した`ChatbotLink.test.tsx`
（`fireEvent.click`実行後に`installFetchMock`が捕捉した実際の`POST /api/events`ボディを
`toEqual`で厳密比較）で確認済み。2テストが該当:
- 「クリック時に chatbot_open イベントのpayloadへ現在の文脈を含める」:
  `{ product_id: "P001", coordinate_id: null, to_product: null, screen: "product_detail" }`
- 「to_product文脈でのクリックはpayloadのto_productに配列が入る」:
  `payload.to_product === ["P001", "P002"]`, `payload.screen === "route"`

（付記）本ブラウザMCPセッションでは`<a>`要素（target="_blank"のChatbotLinkおよび
React Router Link）へのcomputer.left_clickによるクリックイベント配送が確認できず
（`screenshot`ツールも "Browser pane is not displayed" エラーを返す既知の表示合成制約と
整合）、実ブラウザ上でのクリック→POST発火の直接観測はできなかった。同一DOM内の
`<button>`（フロア切替）のクリックは正常に機能し表示が切り替わったことを確認しているため、
これはアプリ側の不具合ではなくブラウザ自動操作ハーネス側の制約と判断する。
クリック→payload生成の正しさはQAが独立実行したコンポーネントテストで担保している
（HARNESS.md「実ブラウザ or コンポーネントテストで確認」の後者に該当）。

判定: **PASS**

## G-P2C-6: 跨フロア経路（4.3・独立実HTTP）

### バックエンド（実HTTP、curl直叩き）

`uvicorn`を起動し、`POST /api/session`でセッションを作成後、以下を実行:

```
GET /api/route?from_qr=QR-ENTRANCE-001&to_product=P011&session_id=<sid>
```
（P011はfloor=2の商品、QR-ENTRANCE-001はfloor=1起点）

応答（`harness/evidence/P2C/http-route-cross-floor.txt`）:
```json
{"waypoints":[
  {"floor":1,"x":3,"y":50,"type":"入口"},
  {"floor":1,"x":10,"y":50,"type":"通路"},
  {"floor":1,"x":30,"y":50,"type":"通路"},
  {"floor":1,"x":50,"y":50,"type":"通路"},
  {"floor":1,"x":50,"y":50,"type":"階段"},
  {"floor":2,"x":50,"y":50,"type":"階段"},
  {"floor":2,"x":50,"y":50,"type":"通路"},
  {"floor":2,"x":30,"y":50,"type":"通路"},
  {"floor":2,"x":20,"y":20,"type":"ゾーン"},
  {"floor":2,"x":17,"y":18,"type":"商品近傍"}
],"visiting_order":["P011"],"unreachable":[],"total_distance":117.23}
```
全waypointに`floor`が含まれ、フロア境界（インデックス4→5、`floor=1`階段→`floor=2`階段）が
階段ノードを経由していることを実HTTPレスポンスで確認。

跨フロア複数目的地（`to_product=P001&to_product=P011`、floor=1とfloor=2の混在）でも
`visiting_order=["P001","P011"]`（最近傍法どおり同フロア優先）、経由フロア`{1,2}`を確認
（`harness/evidence/P2C/http-route-multi-cross-floor.txt`）。
比較対象として単一フロア（P001のみ）はフロア境界を含まない経路が返ることも確認
（`harness/evidence/P2C/http-route-single-floor.txt`、無回帰確認）。

### フロントエンド（実ブラウザ）

`?to_product=P011`（セッションあり）でS4に到達した状態で:
- `floor-switch`（`1F`/`2F`ボタン）が表示される（単一フロア時は表示されないことは
  `RoutePage.test.tsx`で確認済み、G-P2C-3参照）。
- 乗換表示`floor-transfers`のテキストが**「1階→2階（階段）」**と表示される。
- `2F`ボタンをクリックすると（`left_click`成功、フロア切替UIはボタン要素でクリックが機能した）、
  フロアマップが「フロア2のマップ」に切り替わり、目的地ピン
  「ホワイトベッドフレーム シングル」（P011）がフロア2側にのみ描画される。

判定: **PASS**

## 評価環境上の注意点（不具合ではないが記録）

  「the Browser pane is not displayed, so the page is not compositing frames」エラーを返し、
  スクリーンショット証跡は取得できなかった（依頼文にも「スクショ必須ではなく」とあるため

  target="_blank"リンク）へのcomputer.left_clickがクリックイベントとして配送されず、
  ページ遷移・fetch発火が観測できなかった（同一セッション内で`<button>`要素へのクリックは
  正常に機能した）。これはブラウザ自動操作ハーネス側の制約と判断し、該当箇所は
  コンポーネントテスト（QAが独立実行、全PASS）で代替確認した。
- `.claude/launch.json`（`room-harmony/.claude/launch.json`および親フォルダの
  `ニトリ制作物/.claude/launch.json`）をQAが新規作成した。これはブラウザプレビュー起動用の
  設定ファイルであり、アプリの実装コードではない。
