## G-G3-7 詳細（計測の結線）とFAILにしなかった観察事項

`data/room_harmony.db` の `events` テーブルを直接クエリし、上記E2E操作の一連（S1→S2→related_tap→S4→
`/coordinates/C001`→未セッション`/route`）に対応する `session_start`, `qr_scan`, `related_view`,
`related_tap`, `coordinate_view`, `route_view` の各イベントが `experiment_group`
（`treatment`/`control`のいずれか）付きで記録されていることを確認した（AC-4該当）。

**観察事項（FAILではなく実装者への申し送り）**: `npm run dev`（React `<StrictMode>` 有効）で
`ScanPage.tsx` を経由すると、同一QR直リンクの1回の到達に対し **2つの異なる session_id**
（例: `3748deaf.../experiment_group=treatment` と `cce0ac98.../experiment_group=control`）が作成され、
`qr_scan` イベントも2件記録された。原因は `ScanPage.tsx` の `useEffect` 内 `resolveAndEnter` 呼び出しに
`ProductPage.tsx`/`RoutePage.tsx`/`CoordinatePage.tsx` にある `cancelled` ガードが無く、
StrictModeによるeffect二重実行時に両方の非同期処理が最後まで完走してしまうためと推測される。
`related_view`/`route_view`/`coordinate_view` 等サーバ側自動記録イベントも同様に2重記録が発生した
（こちらは各ページに `cancelled` ガードがあるため `setState` は1回に抑えられているが、GETリクエスト自体は
2回発行されるため、サーバ側の自動ログは重複する）。
本現象は `vite build` の本番バンドル（StrictModeのeffect二重実行はReactの仕様上開発ビルド限定）では
発生しない可能性が高いが、`vite preview`（本番ビルド配信, port 4173）で検証しようとしたところ、
バックエンドのCORS許可オリジンが `http://localhost:5173` のみに限定されており(`backend/app/main.py`)、
`http://localhost:4173` からのAPI呼び出しがブロックされたため本番ビルドでの再現有無は**未検証**である。
詳細は `evidence/G3/G-G3-7/events-db-dump.txt` 末尾の「観察事項」を参照。
本件はG3ゲート（build/test/E2E到達）自体の合否には影響しないためPASS判定としたが、
AC-4「正確な」ログという観点およびセッション整合性のデータ品質上の懸念として記録する。
