## E2E ハッピーパス詳細（実施した操作の実際の流れ）

1. **S1（URL直リンク・フォールバック）**: `http://localhost:4173/s/QR-PRODUCT-P001`
   （実在QR `data/qr_codes.json` の `QR-PRODUCT-P001` → `product_id: "P001"`）に
   Claude_Browser MCPでナビゲート → 自動的に `/products/P001`（S2）へ遷移。
2. **S2**: 商品詳細（ナチュラル2人掛けソファ・¥39,900・1Fゾーン A）＋関連商品2件
   （ブラックデスクライト→ホワイトデスクライト、backendの実応答順=lift降順と一致、
   両方「伸びしろ」バッジ付き）＋コーディネート1件（ナチュラルリビング）を確認（AC-1）。
3. **S2→S4**: 関連商品「場所を見る」ボタンをクリック（実クリックイベントで実際に
   `POST /api/events`(related_tap) と `GET /api/route?...to_product=P036...` が
   このブラウザセッションから発行されたことを確認）→ 複数フロア（1F〜4F切替）の
   ルート画面へ遷移。
4. `/products/P001` に戻り、S3（コーディネート詳細, `/coordinates/C001`）へ到達
   （リンクのhrefはDOM確認済み。クリックがこのカード型リンクに対して自動化ツール側で
   不安定だったため直接ナビゲートで到達確認、詳細はAC-2証跡参照）。
5. **S3**: 構成商品4点（ナチュラル2人掛けソファ／ホワイトリビングテーブル／
   ベージュラグ 200x250／ナチュラルクッションカバー）＋合計金額目安¥70,690を確認（AC-2）。
6. **S3→S4**: 「このコーデで揃える／場所を見る」ボタンをクリック（実クリックで
   `GET /api/route?...to_product=P001&to_product=P003&to_product=P007&to_product=P009...`
   が実際に発行されたことを確認）→ 複数目的地ルート画面へ遷移。visiting_order
   （巡回順 P001→P003→P007→P009）が表示され、backend応答の `sub_passages`
   配列が1件（floor=1,x=95,y=88）で非空、すなわち経由サブ通路を含むルートであることを
   ライブAPI応答で確認（AC-3）。
7. 別タブ（sessionStorage空・一度もQRを解決していない真にフレッシュなコンテキスト）で
   `/route?to_product=P001` と `/products/P001` に直接遷移し、来店ロックUI（role="alert"、
   「この機能はご利用いただけません」＋「QRを読み取る」リンク）を確認。`/route` では
   `GET /api/route` が一切発行されていないことも確認（クライアント側ロックが正しく機能）（AC-5）。
8. 上記6.までの一連の操作で使われたセッション（`session_id=f2107d34-...`）を
   backend検証用DBで直接クエリし、`session_start`(1) / `qr_scan`(1) / `related_view`(2) /
   `related_tap`(1) / `route_view`(2) / `coordinate_view`(1) / `coordinate_tap`(1) が
   すべて `experiment_group="control"` 付きで記録されていることを確認（AC-4）。
   `related_view`/`route_view` が2件なのは、それぞれ該当画面を2回訪問した（正当な）
   結果であり、1回の操作に対して複数回記録される重複ではないことをペイロード内容の
   相違（route_viewの `to_product` が1件目は`["P036"]`、2件目は複数目的地）で確認済み。
   **本番ビルドでは session_start・qr_scan がそれぞれ1回のみで、G3で観察された
   開発ビルド限定のStrictMode二重発火は再現しないことを実測確認した。**

## AC-3 の判定根拠についての限定事項（重要・透明性のため明記）

本環境ではPNGスクリーンショットもDOM要素の視覚的確認も取得できなかった
（詳細は下記「Playwrightスクリーンショット取得の可否・環境制約の最終結論」参照）ため、
AC-3の「経路が地図上に線で描画され、経由サブ通路が示される」の判定は、以下3点の
組み合わせによる**間接的だが具体的な根拠**に基づく:

1. **ライブAPI応答**（このブラウザセッションでの実際のレスポンス、curlの再現ではない）:
   `sub_passages: [{floor:1,x:95,y:88}]`（非空）、`waypoints` 14件（>=2）。
2. **ソースコード**（`frontend/src/components/FloorMap.tsx`、読み取りのみ・無改変）:
   `routeWaypoints.length >= 2` で無条件に `<polyline data-testid="route-line">` を描画、
   `subPassagePoints`（空でない）の各要素に対し無条件に
   `<circle data-testid="route-subpassage">` を描画するロジックであることをコードで確認。
   条件分岐に副作用や外部フラグは無く、上記1のデータが渡されれば必ず描画される構造。
3. **既存の自動テスト**（実装から独立してQAが本ゲートで実行し全緑を確認済み）:
   `backend/tests/integration/test_route.py::test_route_destination_via_sub_passage_reports_sub_passage_waypoint`、
   `backend/tests/unit/test_routing.py::test_route_can_include_sub_passage_waypoint`。

DOM上の実際の `<polyline>`/`<circle>` 要素の存在をピクセル単位で目視確認したわけではない点は
限定事項として明記する。もし追加の確証が必要な場合、本環境のSxS問題が解消され次第
Playwrightで再検証することを推奨する。

## Playwrightスクリーンショット取得の可否・環境制約の最終結論

**この環境ではPlaywrightによるヘッドレスPNGスクリーンショットの取得はできなかった。**

- Playwright自体は正しく導入し（`@playwright/test`, `npx playwright install chromium`
  でChromium本体のダウンロード・展開まで正常完了）、テストコードも実装した
  （`frontend/e2e/happy-path.e2e.ts`）。
- しかし `npx playwright test` 実行時、`browserType.launch: spawn UNKNOWN` で
  Chromiumの起動そのものに失敗した。
- 切り分けの結果、**Node.jsのchild_process.spawnや自動化ツールの問題ではなく、
  このWindowsマシンのSxS（side-by-side assembly）解決に関するOS環境固有の問題**
  であることを確認した（Windowsイベントログ ProviderName=SideBySide, EventID=33:
  「Dependent Assembly ... could not be found」、PowerShellの直接起動でも同一の
  「side-by-side configuration is incorrect」エラー）。
- この種の問題の是正（SxSキャッシュ修復・セキュリティソフト除外設定等）は
  システム設定の変更に該当し、QAの権限では実施しない（実施すべきでもない）。
- フォールバックとしてClaude_Browser MCPの `computer{action:"screenshot"}` も
  複数回試行したが、G3から継続する既知の制約（"the Browser pane is not displayed,
  so the page is not compositing frames"）により同様に失敗した。
- そのため本ゲートの証跡は、実ブラウザでの実操作結果（`read_page`/`get_page_text`/
  `read_network_requests` によるDOM状態・実際に発行されたAPIリクエスト/レスポンス
  本文のテキストダンプ）と、バックエンド検証用DBの直接クエリ結果を採用した
  （G3で採用した方針と同一）。

詳細・再現手順: `evidence/G4/AC-6/env-constraints.txt`、
`evidence/G4/AC-6/playwright-run-output.txt`。

## FAIL 詳細（あれば）／実装エージェントへの申し送り

E2Eハッピーパス自体のFAILは無し。ただしAC-6「DoD総合」の一部として、以下2点は
実装エージェントへの申し送り事項として記録する（いずれも今回のPASS判定には
影響しないが、DoDの「README通りに第三者が起動できる」の完全性という観点では
ギャップがある）。

1. **`frontend/package.json` に `test:e2e` スクリプトが存在しない**
   - 期待: `README.md`（6.2節）および `docs/HARNESS.md`（§2, §6）はいずれも
     `cd frontend && npm run test:e2e` をG4の実行コマンドとして明記している。
   - 実際: `frontend/package.json` の `scripts` に `test:e2e` は定義されていない
     （`dev`/`build`/`lint`/`preview`/`gen:api`/`test`/`test:watch` のみ）。
   - 再現手順: `cd frontend && npm run test:e2e` → `npm error Missing script: "test:e2e"`
   - 影響: HARNESS.md記載のコマンドをそのまま実行すると失敗する（本QAは
     `npx playwright test` で直接実行することで回避した）。
   - 提案（実装への申し送りのみ。QAはpackage.jsonのscripts自体は追加していない
     — 独立性維持のため。ただしテストツール自体の追加(`devDependencies`への
     `@playwright/test`追加)はQA側で実施済みなので、スクリプト定義の追加のみで
     解消可能）: `package.json` の scripts に
     `"test:e2e": "playwright test"` を追加。

2. **`README.md` がstep3時点の内容のまま更新されていない**
   - 期待: AC-6「README通りに第三者が起動できる」。
   - 実際: README冒頭に「本READMEは **step3（リポジトリ雛形＝動く空アプリ）** 時点の
     ものです」との記載が残り、6章のテスト実行手順も「現時点(step3)で緑になるのは
     `tests/integration/test_health.py` のみ」「`tests/unit` は後続ステップで追加」等、
     実態（backend単体27件・結合45件が実装済みで全緑、frontend画面・計測ログも
     実装済み）と乖離した記載になっている。8章のステータスチェックリストも
     全項目未達（`[ ]`）のままで、実際には推薦/経路ロジック・API本体・画面実装・
     計測ログ埋め込みまで完了している。
   - 影響: README本文の"現状記述"を読んだ第三者が古い実装状況を前提にしてしまう
     可能性がある（起動コマンド自体（4章）は現行実装でも正しく動作することは
     本ゲートで確認済みなので、**起動不能という意味でのFAILではない**）。
   - 提案: README全体をstep8（またはE2E受け入れ検証完了）時点の内容に更新し、
     6.2節の `npm run test:e2e` 実行手順・8章のステータスチェックリストを実態に
     合わせる。
