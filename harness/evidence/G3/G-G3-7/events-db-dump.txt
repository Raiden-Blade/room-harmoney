観察事項（FAILにはしないが実装者への申し送り事項）:
- id=4/5 と id=6/7 のように、S1（ScanPage）で同一のQR直リンク到達に対し「2つの異なるsession_id」
  （3748deaf.../treatment と cce0ac98.../control）が作成され、qr_scan イベントも2件（experiment_group が
  treatment と control で異なる）記録された。
- 原因: `frontend/src/main.tsx` は React `<StrictMode>` を使用しており、開発ビルド（`npm run dev`）では
  effect が意図的に2回実行される。`ScanPage.tsx` の `useEffect` 内 `resolveAndEnter` 呼び出しは
  `ProductPage.tsx`/`RoutePage.tsx`/`CoordinatePage.tsx` と異なり cancelled ガードが無いため、
  2回の実行がどちらも `createSession` を最後まで実行し、2つの独立したセッション行・qr_scanイベント行を
  作成してしまう（ProductPage等はcancelledガードがあるためsetStateこそ1回に抑えられるが、
  GETリクエスト自体は2回飛び、related_view/route_view/coordinate_view等のサーバ側自動記録イベントは
  やはり重複する）。
- 影響範囲: `npm run dev`（StrictMode有効な開発ビルド）でのみ発生。`vite build` の本番バンドルでは
  StrictModeのeffect二重実行はReactの仕様上発生しない想定（未検証: `vite preview` はバックエンドCORSが
  `http://localhost:5173` のみ許可のため `http://localhost:4173` からは検証不可だった。
  `backend/app/main.py` のCORS許可オリジンをコメントで「本番のオリジンは環境変数化して後続ステップで
  絞り込む」としており、既知の未確定事項）。
- 本観測はG3ゲート自体（build/test/E2E到達）のPASS/FAILを左右するものではないが、AC-4の「正確な」ログ
  という観点、および開発時のセッション整合性（同一QRスキャンで複数セッションが割り当てられうる）の
  データ品質上の懸念として記録する。
